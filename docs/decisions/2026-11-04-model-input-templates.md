# 模型输入模板与机制调整决策

日期：2026-11-04  
状态：已讨论定稿，尚未实施  
适用范围：鱼缸现行模型输入、open 主动轮、GIF 收图、新闻播报、换页历史尾；压缩调用本身不变。

## 1. 背景与证据边界

本次讨论以家中 Mac 生产环境的 `var/fish.db`、chatlog 和 NapCat 调试日志为依据，区分了：

- NapCat 的 QQ NT `RawMessage`；
- NapCat 转换后的 OneBot `OB11Message`；
- 鱼缸持久化的 `fish.inbound.data`；
- 实际交给模型的 `model[0].content`；
- 一次完整 LLM API 请求。

当前数据库完整保存本轮新增 user entry，但没有逐次保存展开 system、全部历史、工具面及 provider 参数后的完整 HTTP 请求快照。不能用代码拼出的推定请求冒充历史原始请求。

历史 `pi.user` 属于旧格式，不再作为现行输入设计依据。现行主要输入记录为 `fish.inbound`、`fish.engage_tick`、`fish.gif_ingest` 等。

## 2. 总体设计原则

1. user 输入采用紧凑的结构化文本，不直接塞入冗长 OneBot JSON。
2. 消息行统一为：

   ```text
   [m:id][可选标签] 昵称(QQ): 正文
   ```

3. `: ` 后永远是当前消息正文；其他信息全部放在 `: ` 前的标签中。
4. 消息列表必须严格符合真实接收顺序：
   - 背景消息不按发送者重排；
   - 合并组保持到达顺序；
   - 当前消息留在真实时间线位置；
   - 引用原文等附加信息放在 `> 消息结束` 后，不参与排序。
5. 标签只陈述事实，标签语义与应对规则统一写入 system prompt，不在每轮 user input 重复解释。
6. 每条消息占一行；引用关系不能混进正文，让模型猜测。
7. 主会话直读与 `look`  fallback 均只能看压缩图，不向模型提供原图。

## 3. 标签合同

消息 ID 与标签连写，昵称前保留一个空格：

```text
[m:1110691775][回复了m:1262165350][这条消息@了你][特别关注] [有人@我](2627618651): 正文
```

已确定的标签语义由 system prompt 定义，例如：

- `[这条消息@了你]`：这条消息必须回复。
- `[回复了m:id]`：当前消息回复了指定历史消息；引用原文在消息列表后的附加信息中。
- `[主人]`：发送者是主人。
- `[特别关注]`：发送者是特别关注对象，具体关注与回应规则由 system prompt 规定。

`回复msg:N` 类旧式文本不再用于新标准。当前消息 ID 只用于引用和追踪，不代表模型可凭 ID 反查消息内容。

## 4. 标准群消息模板

所有普通群消息场景以此为基础：

<!-- input-template:group-reply -->
```text
群里有新消息啦。
> 消息起始
[m:556542960] 最聪明的鱼(2943084870): 那这榜挂着就是纯装饰，写全体并列第一，谁都不好意思说自己排第二
[m:1110691775][回复了m:1262165350][这条消息@了你] [有人@我](2627618651): 惹，我还以为爱莉姐姐要和我回家还要给我油豆腐呢
> 消息结束

[引用原文][m:1262165350] Elysia(3768557204)：「聘礼嘛，就是你要把姐姐领回家总得备点诚意呀，油豆腐就是你的报价啦，刚才那句「算了多来点」我可听见了，一盒起步不许赖账哦♪」
```

关键边界：

- `m:1110691775` 是本轮当前消息；
- `m:1262165350` 是被回复的历史消息；
- 鱼要回应当前正文，不是把引用原文当成新消息；
- 引用原文由宿主根据直接 reply 关系水合，和环境背景是两条独立信息来源。

## 5. 场景模板

### 5.1 单条 @、环境背景与回复链

使用第 4 节标准模板。@ 决定 answer turn；环境背景与直接回复链可同时存在，回复链水合不替代环境注入。

### 5.2 同一发送者合并组与特别关注

连续消息在列表中相邻且保持原顺序，不需要额外解释合并机制：

<!-- input-template:sender-burst-voice -->
```text
群里有新消息啦。
> 消息起始
[m:2128404035] [有人@我](2627618651): [图片 inbound/1793781544076-6ff802.jpg]
[m:82804152] 阿蓝(1066598141): 一只眼瞪成白圈，整张脸都停住了
[m:1838148262] 鲸鲸(302789075): 这表情，像刚被人认错门牌
[m:748201561] 阿蓝(1066598141): 被人叫错名字就这反应，改口都来不及
[m:1799917601][回复了m:1416060502][这条消息@了你][特别关注] ql今天玩什么(2603803040): 推销到我心里了
[m:690734310][特别关注] ql今天玩什么(2603803040): [图片 inbound/1793781566470-911a90.gif]
> 消息结束

[引用原文][m:1416060502] Elysia(3768557204)：「哎呀，认错人啦，对不起呀小狐狸～那刚才那句领养宣言就当我在自我推销好了，不吃鱼食的小狐狸也一样欢迎哦♪」

[本轮要求] 必须使用 say_voice 回复，不要使用文字。
```

### 5.3 主人私聊

私聊沿用同一消息行合同，使用独立开场，不展示原始 JSON：

<!-- input-template:master-private -->
```text
私聊有新消息啦。
> 消息起始
[m:1425302217][主人] MHB(2928390812): 给你收5个视频的权限，去吧，只要是你喜欢的就行
> 消息结束
```

### 5.4 图片输入

为保持消息列表是一段连续文本，不在消息行中间拆入 image block。采用列表内编号、列表后附图。

主会话直读压缩图：

<!-- input-template:inline-image-text -->
```text
群里有新消息啦。
> 消息起始
[m:1064654139] [有人@我](2627618651): [图片#1]
> 消息结束

[图片#1 压缩图]
```

紧随其后附一个压缩后的 image block。权威测试以确定性压缩结果 `compressed-1` 的 base64 为例：

<!-- input-template:inline-image-block -->
```json
{
  "type": "image",
  "data": "Y29tcHJlc3NlZC0x",
  "mimeType": "image/jpeg"
}
```

system prompt 统一说明：`[图片#N]` 与 `[图片#N 压缩图]` 对应，每个压缩图标签后紧跟一个 image block。多图按编号重复。

fallback 视觉模型路径：

<!-- input-template:fallback-image -->
```text
群里有新消息啦。
> 消息起始
[m:1064654139] [有人@我](2627618651): [图片 inbound/1793782479412-17b764.jpg]
> 消息结束

[本轮要求] 使用 look 工具读取消息中的图片。
```

`look` 同样只读取压缩图。

### 5.5 open injection 与窗内 shard

两者使用相同标准群消息模板，不在 user input 中通过不同文案区分 injection/shard，也不重复窗口规则：

<!-- input-template:open-standard -->
```text
群里有新消息啦。
> 消息起始
[m:2123920686] 阿蓝(1066598141): 并列第一这招最省事，谁也不好意思争
> 消息结束
```

没有 `[这条消息@了你]` 时不构成必答；open 中能否沉默、如何接话由 system prompt 决定。

### 5.6 零新增主动轮

零新增轮不再由连续沉默或 nudge 决定，不伪装成“群里有新消息”，使用独立模板：

<!-- input-template:active-empty -->
```text
[主动交流机会]
当前没有新消息。你可以自由决定是否使用 say_* 工具开口。

[可选动作]
调用 bili_hot 去逛 B 站；遇到有意思的视频，可以用 say_words 分享到群里。
```

不预选具体视频，不注入 ammoId，不附加“后续有新的动作可以加在这里”等元说明。

### 5.7 新闻播报

使用独立任务模板，正文保留宿主准备好的成品：

<!-- input-template:news -->
```text
[新闻播报]
「2026-11-04 新闻速递」
▸ AI
· 示例模型发布新能力（人民网）https://example.com/news/ai-1
· 示例芯片开始量产（IT之家）https://example.com/news/chip-2
——以上就是今天的新闻
```

使用 `say_words` 单条发送、保留条目链接和来源署名等要求由 system prompt 规定。

### 5.8 GIF 静默收图

GIF 消息进入标准消息列表，任务放在列表后：

<!-- input-template:gif-ingest -->
```text
群里有新消息啦。
> 消息起始
[m:1111528716] [有人@我](2627618651): [图片 inbound/1793784029351-186453.gif]
> 消息结束

[GIF 收图任务]
使用 look 工具读取 [m:1111528716] 的 GIF 压缩图，判断是否值得收录。
值得收录则使用 meme_add；不值得则保持沉默，不要使用 say_* 工具。
```

实际实现可在此前保留真实环境消息，顺序不变。

### 5.9 合并转发

合并转发不是第五种消息列表，也不把展开后的子消息伪装成群里新收到的消息。父消息仍按真实接收顺序进入标准列表；合集正文作为列表后的附加信息，与引用原文一样不参与时间线重排：

<!-- input-template:forward-direct -->
```text
群里有新消息啦。
> 消息起始
[m:1111529000][转发合集][这条消息@了你] [有人@我](2627618651): 看看这个
> 消息结束

[转发合集 12 条][来自m:1111529000]
> 消息起始
[合集#1] 群友甲(10001): 第一条
[合集#2] 群友乙: 第二条 [图片#1]
> 消息结束
…共 12 条

[图片#1 压缩图]
```

**看合集必须同时 @ 鱼**：单纯引用一条合集不展开、不进模型（主人定案 2026-11-04）。引用合集
并 @ 鱼时，被引的合集才展开成后置附件，其权威输入为：

<!-- input-template:forward-reply -->
```text
群里有新消息啦。
> 消息起始
[m:1111529001][回复了m:1111528999][这条消息@了你] [有人@我](2627618651): 这个合集呢
> 消息结束

[引用原文][m:1111528999] 阿蓝(1066598141): [转发合集]

[转发合集 2 条][来自m:1111528999]
> 消息起始
[合集#1][m:9001] 群友甲(10001): 第一条
[合集#2] 群友乙: 第二条
> 消息结束
```

@ 且提到「合集/转发」时，补展开附件没有可确认的来源消息 ID，不伪造 `[来自m:id]`：

<!-- input-template:forward-recent -->
```text
群里有新消息啦。
> 消息起始
[m:1111529100][这条消息@了你] [有人@我](2627618651): 看看上面的合集
> 消息结束

[转发合集 2 条]
> 消息起始
[合集#1] 群友甲(10001): 第一条
[合集#2] 群友乙: 第二条
> 消息结束
```

背景合集只保留短标记，权威输入为：

<!-- input-template:forward-background -->
```text
群里有新消息啦。
> 消息起始
[m:1111529200] 阿蓝(1066598141): [转发合集（内容略）]
[m:1111529201][这条消息@了你] [有人@我](2627618651): 别理那个，看我
> 消息结束
```

关键边界：

- 父消息的 `: ` 后只放它自己的文字；没有附带文字时使用 `[转发合集]` 内容占位，展开文本不得混入该正文。
- 合集子消息保持 OneBot 返回顺序，以 `[合集#N]` 标记；只有 API 真实提供子消息 ID / QQ 时才附 `[m:id]` / `(QQ)`，不得编造。
- 引用合集并 @ 时，父消息保留 `[回复了m:id]` 与 `[这条消息@了你]`，引用原文中的合集父消息与合集附件分开渲染，不重复展开；补展开最近合集时没有真实来源消息 ID 就不写 `[来自m:id]`。
- 合集附件统一放在消息列表后；同时存在普通引用原文时，先引用原文、再合集附件，最近合集补展开最后。所有附加段都不改变消息列表的真实顺序。
- 子图复用 `[图片#N]`、压缩 image block / `look` fallback 合同，不给模型原图；展开仍最多展示前 10 条、子图最多 2 张，嵌套合集只显示 `[嵌套转发]`，不递归。
- 背景里的合集只保留 `[转发合集（内容略）]` 短标记，不注入子消息；换页尾部只能保留当页模型实际见过的合集附件，不得在压缩时补拉新内容。
- 合集只有一种展开前提：**@ 了鱼**。已裁定的三条路径是——自带合集且 @ 时展开；引用合集且 @ 时展开被引的那条；@ 且文字提到「合集/转发」时补展开本群 10 分钟内最近一条未展开合集。无 @ 的自带合集与无 @ 的引用合集都零成本拒掉（不展开、不进模型；自带合集仍缓存 id 供后续补展开），后者不给任何「回复即指令」的例外：回复只是引用动作，决定展开的是 @。

## 6. 废除的机制

### 6.1 旧账提醒

废除 open 轮旧账机制：

- 不再从剖面或长期记忆提取未兑现事项用于 open 提醒；
- 不再注入旧账列表；
- 不再由旧账或连续沉默触发 nudge；
- 删除 system prompt 中对应的主动提醒规则。

这不等于修改压缩功能；压缩仍可保留 promises 字段。

### 6.2 弹药库与 B 站后台逛轮

弹药库机制暂时关闭，因此同时取消后台逛轮：

- 不在主动轮模板中提弹药库；
- 不再启动 `fish.worker_round`；
- 不再定时或因补货需求拉起后台 B 站会话；
- 不再走“后台抓取 → 入库 → 等窗分享”链路；
- B 站浏览仅由当前群会话在主动交流机会中自行发起。

## 7. 压缩与换页历史

### 7.1 压缩调用保持不变

`prompt/handoff.md` 不修改。压缩时仍将其替换变量后作为单条 user message：

```text
handoff.md 原文
{{transcript}} → 本页对话记录
{{previous}}   → 上一页剖面或“（无）”
```

压缩输出仍为 `threads / promises / mood` JSON，剖面卡片与机械校验不变。

### 7.2 换页历史头

换页不是新建 conversation，而是同一会话 `conversation.reset()` 后形成 `pi.reset` user 历史头。其前部剖面卡片保持原样。以下具体值同时作为权威机械测试模板：

<!-- input-template:history-profile -->
```text
（前情 3 条 · 2026-11-04 10:00 ~ 2026-11-04 10:05）
活跃成员：阿蓝(1066598141)、[有人@我](2627618651)
进行中的话头/梗：
- 「并列第一这招最省事」[m:2123920686] （进行中）
鱼的未完话头与承诺：
- 「我待会儿去看看」（未兑现）
氛围：轻松闲聊
```

尾部不再混杂 `鱼:` 与重复的旧版 open 输入，统一为标准消息列表：

<!-- input-template:history-tail -->
```text
[历史消息]
> 消息起始
[m:2123920686] 阿蓝(1066598141): 并列第一这招最省事
Elysia(3768557204): 我待会儿去看看
[m:2123920695] [有人@我](2627618651): 看完记得说说
> 消息结束
```

鱼自己的行没有 `[m:id]`，这是机械事实而不是格式特权：鱼的话来自 `fish.outbound` entry，entry 里
没有真实消息 id（实际 id 只在发送成功后由 drain 记进 `fish.sentmap`）；历史尾是 entry 的逐字投影，
缺真实 id 就省略锚点，不编造、也不为了好看回头补一条不存在的时间线（与合集子消息“不伪造 ID/QQ”
同一条规则）。群友行照常带锦点。

当页模型实际见过合集时，尾部在完整历史列表后保留该附件。尾部是被压缩页输入的逐字投影，所以父消息行保留 `[转发合集]` 来源标记与 `[这条消息@了你]` 义务标记（与 §5.9 同一套标签；自带合集正是靠 @ 才展开）：

<!-- input-template:history-forward-tail -->
```text
[历史消息]
> 消息起始
[m:2123920700][转发合集][这条消息@了你] 阿蓝(1066598141): [转发合集]
> 消息结束

[转发合集 2 条][来自m:2123920700]
> 消息起始
[合集#1] 群友甲(10001): 第一条
[合集#2] 群友乙: 第二条
> 消息结束
```

尾部规则：

- 群友与鱼使用同一消息行格式：`[m:id][可选标签] 昵称(QQ): 正文`；鱼的行没有真实 id 时省略 `[m:id]` 字段，其余不变；
- 严格保持真实时间顺序；
- 不包含旧版窗口说明、旧账提醒；
- 不包含 thinking、toolCall、toolResult；
- 只保留应进入换页尾部的真实消息原文。

## 8. 本次不做的事

- 不把完整 OneBot JSON 直接作为模型输入；
- 不把 system、历史和工具定义拼成所谓“历史完整请求”；
- 不为了 inline 图片拆散标准消息列表；
- 不给主模型或 fallback 模型提供未压缩原图；
- 不修改现有压缩 prompt 和压缩输出合同。
